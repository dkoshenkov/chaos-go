# Контрольные нагрузочные прогоны

Стенд запускался на Linux/amd64 с лимитом CPU 4 ядра. Генератор, proxy и backend работали в одном Go-процессе на loopback. Включён сбор метрик, журналы запросов отключены. В таблице — один прогон каждого профиля. Результаты описывают этот стенд и его генератор.

| Целевые RPS, доля, тело | Окно | Задержки запрос + ответ | Запущено / предложено | HTTP 200 | HTTP 429 | Отменено клиентом | I/O ошибки | Успешных RPS в окне |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| 100, 0%, 1 KiB | 5s | 0s + 0s | 500 / 500 | 500 | 0 | 0 | 0 | 99.8 |
| 1000, 10%, 100 KiB | 5s | 1s + 1s | 4819 / 5000 | 4819 | 0 | 0 | 0 | 926.8 |
| 5000, 0%, 1 KiB | 5s | 0s + 0s | 24750 / 25000 | 24750 | 0 | 0 | 0 | 4949.0 |
| 100, 50%, 10 MiB, POST | 2s | 10s + 10s | 193 / 200 | 193 | 0 | 0 | 0 | 48.5 |
| 100, 100%, 1 KiB, отмена | 3s | 1m0s + 1m0s | 300 / 300 | 101 | 0 | 199 | 0 | 0.0 |

Генератор пропускает отправки при исчерпании лимита параллельности или отставании от расписания. Колонка RPS учитывает успешные завершения в окне подачи нагрузки. При задержке 60 + 60 секунд все успешные ответы приходят после этого окна. Во всех профилях время ожидания завершения отсчитывалось отдельно.

Базовые значения сняты после открытия двух listeners. Для последнего профиля массовая отмена срабатывала на 2-й секунде, новые запросы в последнюю секунду продолжали выполняться. Дополнительные параметры смешанного профиля: `-max-in-flight 600 -fault-slots 500`. Для последнего профиля: `-fault-slots 512 -cancel-after 2s -drain-timeout 135s`. В профиле с 10 MiB использован `-upload`, размер относится к обоим направлениям. Остальные параметры и определения показателей описаны в [инструкции стенда](README.md).
