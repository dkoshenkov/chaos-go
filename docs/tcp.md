# TCP, Kafka и управление через HTTP-заголовки

Для Kafka с инъекциями по заголовкам используйте режим `connect`. Клиент один раз передаёт HTTP/1.1-запрос `CONNECT` с политикой конкретного сокета. После ответа `200 Connection Established` тот же сокет передаёт байты Kafka в обоих направлениях. Заголовки заканчиваются на прокси. Один туннель может обслужить много Kafka-запросов и сообщений.

## Запуск с обычным Kafka-клиентом

В примере Kafka слушает на `127.0.0.1:9092`. На listener брокера, к которому подключается прокси, нужно настроить advertised-адрес `127.0.0.1:19092`, доступный тестовому клиенту. Из корня репозитория соберите и запустите прокси:

```sh
make build
CHAOS_CONNECTION_RESET_ENABLED=true bin/chaos-proxy \
  -mode connect -listen 127.0.0.1:18080 -upstream tcp://127.0.0.1:9092
```

В другом терминале запустите адаптер. Для каждого подключения клиента он откроет отдельный туннель с указанными заголовками:

```sh
bin/chaos-tunnel -listen 127.0.0.1:19092 \
  -proxy 127.0.0.1:18080 -target 127.0.0.1:9092 \
  -header 'X-Chaos-Request-Delay-Ms: 250' \
  -header 'X-Chaos-Response-Delay-Ms: 500' \
  -header 'X-Chaos-Timeout-Ms: 30000'
```

Укажите `bootstrap.servers=127.0.0.1:19092` у producer и consumer. В этом примере до подключения к брокеру проходит 250 мс, первые байты ответа от брокера задерживаются на 500 мс после их получения прокси, а общее время жизни соединения ограничено 30 секундами. Kafka-клиент может автоматически переподключиться. Каждое новое соединение проходит новую проверку заголовков и вероятности. Чтобы одновременно тестировать несколько политик, можно запустить адаптеры с разными заголовками на разных портах или передавать заголовки напрямую при каждом `CONNECT`.

Готовый пример с настоящим брокером создаёт топик, отправляет сообщение и читает его через адаптер. [Docker Compose и команды проверки](../tests/e2e/kafka/README.md)

### Почему важен advertised.listeners

Bootstrap используется для получения метаданных. Затем Kafka-клиент подключается к адресам лидеров партиций и координаторов групп, которые вернули брокеры. Для каждого доступного клиенту брокера нужен свой стабильный адрес, ведущий через прокси именно к этому брокеру. Для нескольких брокеров разверните по паре «адаптер + прокси» на брокер и укажите соответствующие адреса адаптеров в клиентских `advertised.listeners`. Для inter-broker и controller трафика сохраните отдельные внутренние listeners. Прокси пересылает метаданные Kafka без изменений.

SASL и TLS Kafka проходят внутри туннеля. При TLS сертификат брокера должен быть действителен для имени, которое использует Kafka-клиент. HTTP-заголовки установки туннеля передаются до Kafka TLS. Канал от адаптера до прокси размещайте в доверенной сети или защищайте отдельно. Доступ к порту адаптера даёт возможность использовать настроенную на нём политику.

## Политика одного туннеля

| Заголовок | Действие |
|---|---|
| `X-Chaos-Request-Delay-Ms` | Однократная задержка перед подключением к брокеру. |
| `X-Chaos-Response-Delay-Ms` | Однократная задержка перед передачей первых байтов от брокера к клиенту. HTTP 200 подтверждает туннель сразу после подключения к брокеру, и клиент уже может отправлять данные. |
| `X-Chaos-Timeout-Ms` | Общий срок жизни туннеля, включая установку, задержки и передачу данных. Ноль отключает тайм-аут. Максимум задаёт `CHAOS_TUNNEL_TIMEOUT_MAX` / `chaos.tunnel_timeout.max`, по умолчанию `120s`. |
| `X-Chaos-Connection-Reset` | При `true` и `CHAOS_CONNECTION_RESET_ENABLED=true` обрывает выбранное соединение. При `CHAOS_CONNECTION_RESET_AFTER_BYTES=0` обрыв происходит до HTTP 200 и до обращения к брокеру. При положительном пороге отсчитываются байты от брокера к клиенту за весь туннель. |
| `X-Chaos-Probability` | При включённом механизме вероятность от 0 до 1 применяется один раз ко всей политике соединения. |
| `X-Chaos-Request-Jitter-Ms`, `X-Chaos-Response-Jitter-Ms` | При включённом механизме изменяют задержку соответствующего направления. |
| `X-Chaos-Token` | Авторизация заголовков управления. Если на прокси задан `CHAOS_TOKEN`, передайте тот же секрет в окружении адаптера. |

Для проверки немедленного обрыва добавьте адаптеру `-header 'X-Chaos-Connection-Reset: true'`. Для проверки обрыва после начала обмена задайте прокси, например, `CHAOS_CONNECTION_RESET_AFTER_BYTES=1024` и переподключите клиент. Порог относится к байтам на проводе, включая Kafka handshake и, при использовании TLS, зашифрованные записи.

Задержка ответа применяется один раз к TCP-потоку. Например, при Kafka поверх TLS первыми байтами от брокера может быть TLS handshake. Для проверки отдельного Produce или Fetch внутри уже установленного потока потребуется учитывать границы запросов Kafka.

Клиент с поддержкой CONNECT может обращаться к прокси напрямую. Пример начала обмена:

```http
CONNECT broker.internal:9092 HTTP/1.1
Host: broker.internal:9092
X-Chaos-Request-Delay-Ms: 250
X-Chaos-Timeout-Ms: 5000

```

В адаптере `-handshake-timeout` ограничивает ожидание подключения к прокси и ответа CONNECT (по умолчанию 5 минут). После HTTP 200 этот таймер снимается, и обе стороны могут независимо закрывать направление записи (TCP half-close). Если клиент закрыл запись до подтверждения туннеля и не передал полезных данных, ожидающее подключение отменяется.

В этом примере upstream оператора должен быть `broker.internal:9092`. Прокси проверяет запрошенный адрес и соединяется только с настроенным upstream. В режиме CONNECT заголовки искусственного HTTP-статуса и ограничения полосы возвращают HTTP 400 при включённом chaos. Некорректные или неподдерживаемые параметры отклоняются до установки туннеля. Если срок туннеля истёк до его установления, прокси отвечает HTTP 504. После HTTP 200 завершение по тайм-ауту или обрыв видны клиенту как закрытие соединения. Срок жизни отсчитывается один раз: обмен данными не продлевает таймер. Когда включены инъекции и listener доступен за пределами loopback, задайте `CHAOS_TOKEN`. Шлюз между клиентом и прокси должен поддерживать CONNECT.

## Переключение инъекций на открытых туннелях

В режиме CONNECT служебный порт принимает `PUT /connect/policy` и `DELETE /connect/policy`. PUT задаёт политику для открытых и последующих туннелей этого экземпляра прокси. DELETE снимает её и сразу отпускает данные, ожидающие из-за этой политики. Заголовки конкретного CONNECT задают отдельную политику, которая применяется вместе со служебной.

Включите задержку в обе стороны, а затем снимите её на том же соединении. Здесь служебный порт слушает на `127.0.0.1:9090`.

```sh
curl -fsS -X PUT http://127.0.0.1:9090/connect/policy \
  -H 'X-Chaos-Request-Delay-Ms: 250' \
  -H 'X-Chaos-Response-Delay-Ms: 500'

curl -fsS -X DELETE http://127.0.0.1:9090/connect/policy
```

Оба метода возвращают `204 No Content`. Если задан `CHAOS_TOKEN`, передавайте `-H "X-Chaos-Token: ${CHAOS_TOKEN}"` с каждым запросом. Без токена API доступен при буквальном loopback-адресе служебного listener. API требует `CHAOS_ENABLED=true`.

PUT принимает заголовки из таблицы выше и `X-Chaos-Pause` и проверяет действующие лимиты. Повторный PUT с теми же параметрами сохраняет текущую активацию. При изменении параметров прокси заново выбирает туннели по заданной вероятности и сэмплирует jitter отдельно для каждого выбранного туннеля. При достижении `CHAOS_MAX_ACTIVE_FAULTS` туннели без свободного слота продолжают передачу без служебной инъекции до следующего изменения политики.

- Задержка и jitter действуют на каждый блок данных в указанном направлении. Блоки определяет TCP relay.
- Тайм-аут отсчитывается с момента активации политики на туннеле. Замена или снятие политики отменяет её таймер.
- Reset с нулевым порогом обрывает туннель сразу. Положительный порог отсчитывается по байтам от брокера к клиенту с момента активации. Снятие политики сохраняет соединение, пока обрыв ещё не сработал.

### Пауза передачи

`X-Chaos-Pause: true` на служебном PUT приостанавливает пересылку в обе стороны и оставляет туннель открытым. Очередь ограничена буфером прокси и TCP-буферами. Когда они заполняются, отправитель получает backpressure. DELETE или PUT с новой политикой без паузы продолжает передачу накопленных байтов в прежнем порядке. Уже переданные в сокет получателя байты могут дойти после включения паузы.

```sh
curl -fsS -X PUT http://127.0.0.1:9090/connect/policy \
  -H 'X-Chaos-Pause: true'

curl -fsS -X DELETE http://127.0.0.1:9090/connect/policy
```

Для паузы с последующим обрывом добавьте к PUT заголовок `X-Chaos-Timeout-Ms`. Например, `X-Chaos-Timeout-Ms: 5000` закрывает туннель после пяти секунд тишины. Без тайм-аута сама пауза действует до снятия или замены политики.

## Прямое TCP-проксирование

Если управление заголовками не требуется, клиент может отправлять бинарный протокол напрямую:

```sh
bin/chaos-proxy -mode tcp -listen 127.0.0.1:19092 -upstream tcp://127.0.0.1:9092
```

В этом режиме входные байты сразу идут в фиксированный upstream, включая TLS handshake. Конфигурация оператора позволяет включить статический обрыв выбранных соединений через `CHAOS_CONNECTION_RESET_ENABLED`, `CHAOS_CONNECTION_RESET_AFTER_BYTES` и, при необходимости, `CHAOS_PROBABILITY_ENABLED` / `CHAOS_PROBABILITY_DEFAULT`. Для выборочной политики через заголовки используйте `-mode connect`.

Режим также можно задать через `SERVER_MODE` или `server.mode` в YAML. HTTP reverse proxy остаётся режимом по умолчанию. У всех режимов есть отдельный служебный listener. На нём доступны метрики `chaos_proxy_tcp_active_connections`, `chaos_proxy_tcp_connections_total`, `chaos_proxy_tcp_bytes_total` и `chaos_proxy_tcp_connection_duration_seconds`.

## Helm

Для отдельного релиза, который принимает CONNECT на порту 18080 и направляет трафик на первый брокер, задайте следующие значения. Secret с ключом `token` должен существовать в том же namespace.

```yaml
mode: connect
service:
  port: 18080
upstreamURL: tcp://kafka-0.kafka-headless:9092
chaos:
  existingSecret:
    name: chaos-credentials
  connectionReset:
    enabled: true
  tunnelTimeout:
    max: 120s
```

Примените values для [Helm chart](../deploy/helm/chaos-proxy). Адрес этого Service используется в `-proxy` адаптера, адрес из `upstreamURL` без схемы — в `-target`. Служебные HTTP probes остаются на отдельном порту.
