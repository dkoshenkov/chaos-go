# HTTP Chaos Proxy

Reverse proxy на Go для тестирования тайм-аутов и отмены HTTP-запросов. Клиент задаёт задержки, ошибки, ограничение полосы и обрыв соединения в заголовках отдельного запроса. Адрес backend задаёт оператор при запуске. Для локального запуска достаточно Go 1.25 или новее и HTTP- или HTTPS-сервиса, к которому можно отправить тестовый запрос.

Для Kafka и других бинарных протоколов доступны режимы `tcp` и `connect`. В режиме `connect` заголовки `X-Chaos-*` управляют задержками, тайм-аутом и обрывом отдельного TCP-соединения. [Запуск перед Kafka и примеры заголовков](docs/tcp.md)

## Локальный запуск

В примере backend слушает на порту 9000. В корне репозитория выполните:

```sh
go run ./cmd/chaos-proxy -upstream http://127.0.0.1:9000
```

В другом терминале отправьте запрос:

```sh
curl -i -w '\nДо первых байтов: %{time_starttransfer} с\n' \
  -H 'X-Chaos-Request-Delay-Ms: 2000' \
  -H 'X-Chaos-Response-Delay-Ms: 3000' \
  'http://127.0.0.1:8080/items?limit=5'
```

Backend получит этот запрос через две секунды или позже. Когда backend вернёт заголовки, прокси выждет ещё три секунды перед отправкой итогового статуса, заголовков и тела клиенту. Таким образом, до первых байтов итогового ответа пройдёт как минимум пять секунд плюс время самого backend. Тело передаётся потоком. Для сравнения отправьте тот же запрос без заголовков задержки.

| Заголовок | Значение и действие |
|---|---|
| `X-Chaos-Request-Delay-Ms` | Целое число миллисекунд от 0 до максимума включительно. Ожидание до обращения к backend. |
| `X-Chaos-Response-Delay-Ms` | Такой же диапазон. Ожидание после получения заголовков backend. |
| `X-Chaos-Status-Code` | Итоговый HTTP-статус от 200 до 599. Прокси сам возвращает пустой ответ без обращения к backend. |
| `X-Chaos-Probability` | Число от 0 до 1. Значение `0.3` применяет все заданные инъекции приблизительно к 30% запросов. |
| `X-Chaos-Request-Jitter-Ms`, `X-Chaos-Response-Jitter-Ms` | Амплитуда случайного отклонения задержки, целое число миллисекунд. Для каждой стороны отклонение выбирается отдельно из диапазона от −J до +J. Результат ограничен нулём и максимумом задержки. |
| `X-Chaos-Request-Bandwidth-Kbps`, `X-Chaos-Response-Bandwidth-Kbps` | Ограничение скорости передачи тела в выбранном направлении для одного запроса. Целое число от 1 до 1 000 000 в десятичных кбит/с. Например, 800 кбит/с соответствует 100 000 байт/с. |
| `X-Chaos-Connection-Reset` | Значение `true` вызывает обрыв до заголовков или во время передачи тела согласно настройке `after_bytes`. |
| `X-Chaos-Enabled` | Маркер для маршрутизации в Istio. При прямом обращении достаточно заголовков задержки. |
| `X-Chaos-Token` | Секрет для авторизации управляющих заголовков, если оператор задал `CHAOS_TOKEN`. |

Прокси удаляет управляющие заголовки перед пересылкой. Метод, путь, параметры запроса, тело и сквозные HTTP-заголовки передаются backend. Заголовок `Host` соответствует backend, а прокси заново формирует стандартные `X-Forwarded-For`, `X-Forwarded-Host` и `X-Forwarded-Proto`. Если в адресе backend задан префикс пути, прокси добавляет к нему путь запроса.

## Конфигурация и доступ

Пример конфигурации находится в [configs/config.yaml](configs/config.yaml). Порядок применения настроек, от базовых к приоритетным: встроенные значения, YAML из `-config`, переменные окружения, явно указанные флаги `-listen` и `-upstream`. Существующая команда `go run .` также поддерживается.

| Переменная | Назначение | По умолчанию |
|---|---|---|
| `UPSTREAM_URL` | Фиксированный адрес backend | Обязателен через конфигурацию, окружение или флаг |
| `SERVER_LISTEN` | Адрес для клиентских запросов | `127.0.0.1:8080` |
| `OBSERVABILITY_LISTEN` | Отдельный служебный адрес | `127.0.0.1:9090` |
| `CHAOS_ENABLED` | Глобальное включение обработки инъекций | `true` |
| `CHAOS_REQUEST_DELAY_ENABLED`, `CHAOS_RESPONSE_DELAY_ENABLED` | Разрешение задержек каждого направления | `true` |
| `CHAOS_REQUEST_DELAY_MAX`, `CHAOS_RESPONSE_DELAY_MAX` | Максимум для каждого направления | `120s` |
| `CHAOS_ABORT_ENABLED` | Разрешить искусственный HTTP-статус | `false` |
| `CHAOS_PROBABILITY_ENABLED`, `CHAOS_PROBABILITY_DEFAULT` | Вероятностный отбор и вероятность при отсутствии заголовка | `false`, `1.0` |
| `CHAOS_REQUEST_JITTER_ENABLED`, `CHAOS_RESPONSE_JITTER_ENABLED` | Разрешить jitter соответствующей задержки | `false` |
| `CHAOS_REQUEST_BANDWIDTH_ENABLED`, `CHAOS_RESPONSE_BANDWIDTH_ENABLED` | Разрешить ограничение скорости соответствующего тела | `false` |
| `CHAOS_CONNECTION_RESET_ENABLED`, `CHAOS_CONNECTION_RESET_AFTER_BYTES` | Разрешить обрыв и указать число байтов тела ответа до обрыва | `false`, `0` |
| `CHAOS_MAX_ACTIVE_FAULTS` | Максимум одновременных запросов с инъекцией на экземпляр | `1000` |
| `CHAOS_TOKEN` | Секрет для запросов с управляющими заголовками | Пустой |

При включённых инъекциях для прослушивания за пределами loopback требуется токен. Если ingress публикует локальный listener, задайте токен и для loopback. Передавайте токен по защищённому соединению до доверенного ingress, храните его в секрете среды развёртывания и ограничьте доступ к служебному порту. Клиентские запросы без управляющих заголовков проксируются обычным образом. Для отключения всех инъекций установите `CHAOS_ENABLED=false` и перезапустите процесс. В этом режиме управляющие заголовки игнорируются и удаляются перед пересылкой.

| Результат | Причина |
|---|---|
| `400 Bad Request` | Недопустимое, повторное или превышающее лимит значение, неизвестный заголовок `X-Chaos-*` либо отключённый механизм. |
| `403 Forbidden` | Для управляющего запроса требуется токен, а предоставленные учётные данные не прошли проверку. |
| `429 Too Many Requests` | Все слоты инъекций заняты. Запросы без инъекций и запросы, пропущенные вероятностным отбором, проходят в backend. |
| `502 Bad Gateway` | Ошибка соединения с backend или получения его ответа. |
| `504 Gateway Timeout` | Истёк тайм-аут соединения или ожидания заголовков backend. |

Отключение клиента отменяет ожидание и освобождает ресурсы. В Linux при задержке или ограничении скорости HTTP/1.x-запроса с телом прокси дополнительно проверяет TCP-соединение каждые 50 мс. TCP FIN (в том числе клиентский `CloseWrite`) завершает такой запрос. На остальных ОС используется контекст `net/http`: для HTTP/1.x с непрочитанным телом он может обнаружить отключение лишь после окончания задержки. В HTTP/2 отмена действует на отдельный поток. При SIGTERM или SIGINT прокси прекращает приём новых запросов и даёт активным запросам время до `server.shutdown_timeout` на завершение.

## Наблюдаемость

| GET на служебном порту | Назначение |
|---|---|
| `/healthz` | Проверка процесса независимо от доступности backend |
| `/readyz` | Готовность к обработке запросов |
| `/metrics` | Метрики в формате Prometheus |
| `/version` | Версия сборки |

Для сравнения задержек используйте гистограммы `chaos_proxy_upstream_duration_seconds` (от отправки upstream-запроса до получения заголовков), `chaos_proxy_injected_delay_seconds` (фактическое ожидание) и `chaos_proxy_request_duration_seconds` (полное время запроса). При отмене фактическое ожидание может оказаться короче запрошенного. Серия `chaos_proxy_active_faults` отражает занятые слоты. Счётчик `chaos_proxy_injections_total` показывает применения механизмов по `fault_type` и `direction`. JSON-журнал связывает длительности, статус и отмену одного запроса по `request_id`. Поле `applied_faults` перечисляет применённые механизмы. При обрыве до итоговых заголовков в журнале будет `status_code: 0`, а при обрыве во время чтения тела — уже отправленный статус.

## Статус, вероятность и сочетание инъекций

При включённых `CHAOS_ABORT_ENABLED=true` и `CHAOS_PROBABILITY_ENABLED=true` следующий запрос с вероятностью 0.3 получит `503` после задержки в 200 мс. Остальные запросы с теми же заголовками пройдут в backend без этой задержки.

```sh
curl -i http://127.0.0.1:8080/items \
  -H 'X-Chaos-Probability: 0.3' \
  -H 'X-Chaos-Status-Code: 503' \
  -H 'X-Chaos-Response-Delay-Ms: 200'
```

Прокси проверяет заголовки до вероятностного отбора. Для выбранного запроса все инъекции вместе занимают один слот. Сначала применяется задержка запроса с учётом jitter. Затем прокси формирует искусственный статус или отправляет запрос в backend. Задержка ответа заканчивается до отправки итоговых заголовков. Ограничения скорости действуют на потоковую передачу тела в соответствующем направлении. Jitter требует включённого механизма задержки для той же стороны.

## Как проверить обрыв соединения

Для локальной проверки запустите прокси с разрешённым обрывом:

```sh
CHAOS_CONNECTION_RESET_ENABLED=true \
  go run ./cmd/chaos-proxy -upstream http://127.0.0.1:9000
```

В другом терминале выполните:

```sh
curl --http1.1 -v -H 'X-Chaos-Connection-Reset: true' http://127.0.0.1:8080/items
```

При `CHAOS_CONNECTION_RESET_AFTER_BYTES=0` прокси обрывает обмен до итоговых заголовков, без обращения к backend. При прямом подключении по HTTP/1.1 клиент получает разрыв TCP-соединения. При HTTP/2 сбрасывается только выбранный поток. За ingress клиент может увидеть ответ самого шлюза, например `502`.

Чтобы проверить прерванное скачивание, задайте при запуске `CHAOS_CONNECTION_RESET_AFTER_BYTES=1024` и повторите запрос к ресурсу больше 1024 байт. Клиент может уже получить статус `200`: ошибку следует проверять при чтении тела до конца. Порог отсчитывается по байтам тела, отправленным прокси. Ответы размером до порога включительно завершаются штатно. Для потока неизвестной длины обрыв происходит, когда backend передаёт следующий байт после порога. Настройки YAML — `chaos.connection_reset.enabled` и `chaos.connection_reset.after_bytes`. Сочетание искусственного статуса и включённого обрыва в одном запросе вернёт `400`.

## Docker, Kubernetes и Istio

Соберите образ командой `make docker-build IMAGE=chaos-proxy:dev`. Контейнер работает от UID 65532. Для запуска в Kubernetes загрузите образ в реестр, доступный кластеру. Для сборки за корпоративным модульным прокси с собственным УЦ BuildKit принимает публичный CA-сертификат через `docker build --secret id=go_download_ca,src=/path/to/ca.pem -t chaos-proxy:dev .`. Он используется только для загрузки Go-модулей. Chart создаёт Deployment с probes на отдельном порту и ClusterIP Service для клиентского трафика.

```sh
helm upgrade --install chaos-proxy deploy/helm/chaos-proxy \
  --set-string image.repository=registry.example.com/chaos-proxy \
  --set-string image.tag=v1 \
  --set-string upstreamURL=http://backend:8080 \
  --set-string chaos.existingSecret.name=chaos-credentials
```

Для тестирования обрыва через Helm добавьте `--set chaos.connectionReset.enabled=true` и при необходимости `--set chaos.connectionReset.afterBytes=1024`. В файле Helm values большие пороги `afterBytes` (от 2⁵³) указывайте десятичной строкой в кавычках. Укажите свой образ и существующий Secret в namespace релиза. По умолчанию токен читается из ключа `token`. Если имя Secret не задано, chart запускает прокси с глобально отключёнными инъекциями.

При использовании Istio адаптируйте host, gateway, namespace и имена Service в [примере VirtualService](deploy/istio/virtualservice.yaml). Запрос с `X-Chaos-Enabled: true` пойдёт через прокси, остальные — напрямую в backend. Для выбранного маршрута Istio не повторяет запросы. Upstream прокси должен указывать на внутренний Service backend, чтобы запрос не вернулся на тот же ingress-маршрут.

```sh
curl 'https://app.example.com/items' \
  -H 'X-Chaos-Enabled: true' \
  -H "X-Chaos-Token: ${CHAOS_TOKEN}" \
  -H 'X-Chaos-Response-Delay-Ms: 500'
```
